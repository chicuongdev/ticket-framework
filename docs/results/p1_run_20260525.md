### 3.3 SyncOrchestrator.executeFlow() — luồng sync saga

`hcr-product/ms-order/.../saga/TicketBookingSyncOrchestrator.java:56-80`:

```java
@Override
protected TicketOrder executeFlow(SagaContext<TicketOrder> context) {
    TicketOrder order = context.getOrder();

    // [A] Save order PENDING xuống DB
    order = saveOrder(order);             // INSERT ticket_orders (status=PENDING)
    context.setOrder(order);

    // [B] Step 1: Reserve inventory (DB — SELECT FOR UPDATE, blocking)
    onReserving(order);
    StepResult reserveResult = getReservationStep().execute(context);
    if (!reserveResult.isSuccess()) {
        context.markStepFailed("reservation");
        return cancelOrder(context, reserveResult.getFailureReason(), ...);
    }
    context.markStepCompleted("reservation");

    // [C] Transition PENDING → RESERVED
    OrderAccessor.transitionTo(order, OrderStatus.RESERVED);
    order = saveOrder(order);             // UPDATE ticket_orders SET status='RESERVED'
    context.setOrder(order);

    // [D] Step 2+3: Payment + Confirmation
    return executePaymentAndConfirmation(context);
    //   ├─ getPaymentStep().execute(context)  — HTTP POST → ms-payment
    //   │     nếu fail → compensate() → kết thúc CANCELLED
    //   └─ OrderAccessor.transitionTo(order, OrderStatus.CONFIRMED)
    //      saveOrder(order)                    — UPDATE status='CONFIRMED'
}
```

**Transaction boundary** (rất quan trọng):
- `saveOrder()` mở/đóng 1 transaction nhỏ qua Spring Data JPA (default propagation REQUIRED).
- Vì không có outer transaction, mỗi `saveOrder()` là 1 transaction độc lập.
- `getReservationStep().execute()` cũng không wrap thêm transaction ngoài → reserve sẽ có transaction riêng của nó.

```java
@Override
public void compensate(SagaContext<O> context) {
    O order = context.getOrder();
    try {
        inventoryStrategy.release(
                order.getResourceId(), order.getOrderId(), order.getQuantity());
    } catch (Exception e) {
        log.error("[Saga] Release failed (compensate), Reconciliation will fix: orderId={}",

```

`compensate()` bọc try-catch nuốt mọi exception → đây là **chỗ leak được "che giấu"**: release fail → log error → caller không biết → saga vẫn complete bình thường → order CANCELLED nhưng inventory chưa được +1 lại.

### 3.5 PessimisticLockStrategy.reserve() — full code

`hcr-inventory/.../strategy/pessimistic/PessimisticLockStrategy.java:65-115`:

```java
@Override
public ReservationResult reserve(String resourceId, String requestId, int quantity) {
    metrics.recordReserveAttempt(resourceId, STRATEGY_NAME);
    long start = System.currentTimeMillis();

    ReservationResult result = transactionTemplate.execute(status -> {
        //
        // ╔═════════════════════════════════════════════════════════╗
        // ║ ENTERED NEW TRANSACTION (propagation REQUIRED + no outer)║
        // ║   EntityManager bound to this transaction               ║
        // ║   L1 cache = empty                                       ║
        // ╚═════════════════════════════════════════════════════════╝

        // [R1] Load entity với PESSIMISTIC_WRITE lock
        //      SQL: SELECT * FROM concert_tickets WHERE resource_id=? FOR UPDATE
        //      Đợi nếu row đang bị lock bởi transaction khác.
        AbstractInventoryEntity entity = entityManager.find(
            entityClass, resourceId, LockModeType.PESSIMISTIC_WRITE);

        if (entity == null) throw new IllegalArgumentException(...);

        // [R2] Check inventory
        if (entity.getAvailable() < quantity) {
            return ReservationResult.insufficient(resourceId, quantity);
        }

        // [R3] Mutate managed entity — dirty tracking
        long newAvailable = entity.getAvailable() - quantity;
        entity.setAvailable(newAvailable);          // dirty: available
        entity.setUpdatedAt(Instant.now());         // dirty: updated_at
        entityManager.merge(entity);                // managed → no-op

        // [R4] Publish event (Spring sync event — chạy ngay trong tx này)
        if (newAvailable == 0) {
            eventPublisher.publishEvent(new ResourceDepletedEvent(...));
        }
        eventPublisher.publishEvent(new ResourceReservedEvent(...));

        return ReservationResult.success(resourceId, quantity, newAvailable);

        // ╔═════════════════════════════════════════════════════════╗
        // ║ TRANSACTION COMMIT (xảy ra sau khi lambda return):       ║
        // ║  1. Hibernate FLUSH:                                     ║
        // ║     UPDATE concert_tickets SET available_quantity=?,     ║
        // ║       version=version+1, updated_at=?                    ║
        // ║       WHERE id=? AND version=?                           ║
        // ║     (param version=X — value loaded ở [R1])              ║
        // ║  2. COMMIT: row v=X → v=X+1, lock released.              ║
        // ║  3. EntityManager closed, L1 cache discarded.            ║
        // ╚═════════════════════════════════════════════════════════╝
    });
    ...
}
```

### 3.6 PessimisticLockStrategy.release() — full code

`hcr-inventory/.../strategy/pessimistic/PessimisticLockStrategy.java:117-140`:

```java
@Override
public void release(String resourceId, String requestId, int quantity) {
    transactionTemplate.execute(status -> {
        //
        // ╔═════════════════════════════════════════════════════════╗
        // ║ ENTERED NEW TRANSACTION (propagation REQUIRED + no outer)║
        // ║   New EntityManager, fresh L1 cache                      ║
        // ╚═════════════════════════════════════════════════════════╝

        // [L1] Load fresh từ DB (lock PESSIMISTIC_WRITE)
        //      SQL: SELECT * FROM concert_tickets WHERE resource_id=? FOR UPDATE
        //      Giờ DB đã có v=X+1 (từ reserve trước đó).
        //      Nếu reserve chưa commit hoặc đang lock → đợi.
        AbstractInventoryEntity entity = entityManager.find(
            entityClass, resourceId, LockModeType.PESSIMISTIC_WRITE);

        if (entity == null) throw new IllegalArgumentException(...);

        // [L2] Mutate (+ quantity = trả vé lại kho)
        long newAvailable = entity.getAvailable() + quantity;
        entity.setAvailable(newAvailable);
        entity.setUpdatedAt(Instant.now());
        entityManager.merge(entity);

        // [L3] Publish event
        eventPublisher.publishEvent(new ResourceReleasedEvent(...));
        return null;

        // ╔═════════════════════════════════════════════════════════╗
        // ║ TRANSACTION COMMIT:                                      ║
        // ║   UPDATE concert_tickets SET available_quantity=?,       ║
        // ║     version=version+1, updated_at=?                      ║
        // ║     WHERE id=? AND version=?                             ║
        // ║   (param version=X+1 — value loaded ở [L1])              ║
        // ║   DB hiện cũng X+1 → match → UPDATE thành công, v=X+2.   ║
        // ╚═════════════════════════════════════════════════════════╝
    });
}
```

### 3.7 Saga compensation orchestration

`hcr-saga/.../orchestrator/AbstractSagaOrchestrator.java:329-360`:

```java
protected void compensate(SagaContext<O> context) {
    O order = context.getOrder();
    List<String> completed = context.getCompletedSteps();
    if (completed.isEmpty()) return;

    // Compensate theo thứ tự NGƯỢC (LIFO)
    for (int i = completed.size() - 1; i >= 0; i--) {
        String stepName = completed.get(i);
        try {
            switch (stepName) {
                case "payment"      -> getPaymentStep().compensate(context);     // refund
                case "reservation"  -> getReservationStep().compensate(context); // release
                case "confirmation" -> getConfirmationStep().compensate(context);
            }
        } catch (Exception e) {
            log.error("[Saga] Compensate failed for step {}, continuing: orderId={}",
                    stepName, order.getOrderId(), e);
        }
    }
}
```

`compensate()` được gọi từ `executeFlow()` khi PaymentStep fail. Bọc try-catch tại đây cũng nuốt exception nếu có.

## 4. THEORY — Tại sao leak KHÔNG NÊN xảy ra

Theo flow vẽ ở Section 3, ta sẽ chứng minh: dưới giả định "không có code path khác chạm vào ConcertTicket entity giữa reserve và release", **leak không thể xảy ra**.

### Timeline mong đợi (single order, payment fail)

```
t=0:  HTTP POST /orders                            ─┐
                                                    │ no outer transaction
t=1:  saveOrder(PENDING)                            │  tx1: INSERT ticket_orders, commit
                                                    │
t=2:  reserve() entered ──── tx2 begin              │
      [R1] SELECT FOR UPDATE concert_tickets v=X    │
           (acquire row lock)                       │
      [R3] mutate available -= 1                    │
      tx2 commit ──── UPDATE WHERE v=X → v=X+1      │
           (row lock released, EntityManager closed)│
                                                    │
t=3:  saveOrder(RESERVED) ──── tx3 commit          │
                                                    │
t=4:  paymentStep.execute() ──── HTTP to ms-payment │
      → ms-payment trả PaymentResult.FAILED         │
                                                    │
t=5:  saga.compensate() entered                     │
      stepName = "reservation"                      │
      reservationStep.compensate()                  │
        ↓                                           │
      release() entered ──── tx4 begin              │
      [L1] SELECT FOR UPDATE concert_tickets        │
           (acquire row lock — không ai khác hold)  │
           Reads v=X+1 (fresh từ DB)                │
      [L2] mutate available += 1                    │
      tx4 commit ── UPDATE WHERE v=X+1 → v=X+2     │
           thành công vì DB cũng đang v=X+1         │
                                                    │
t=6:  cancelOrder() → status CANCELLED              │
      tx5: UPDATE ticket_orders SET status='CANCELLED'
                                                    │
t=7:  HTTP 201 (CANCELLED) trả về client            │
                                                    ┘
```

Theo timeline này:
- Mỗi `transactionTemplate.execute()` mở **transaction mới, EntityManager mới, L1 cache mới** (vì controller không có @Transactional).
- Reserve commit v=X→X+1.
- Release đọc fresh v=X+1, UPDATE WHERE v=X+1 → match → thành công.
- **Không có lý do gì để `StaleObjectStateException` xảy ra.**

### Inventory accounting kỳ vọng

```
Reserved 1, released 1, net change = 0 → sold không đổi cho mỗi CANCELLED order.
sold = COUNT(CONFIRMED) — chính xác, zero leak.
```

→ Đây là lý do user (bạn) hợp lý khi đặt câu hỏi: "tại sao vẫn leak?"

### 5.1 Bằng chứng

Từ `journalctl -u hcr-order` lúc 18:01:43:

```
       .ModelMutationHelper.checkResults(ModelMutationHelper.java:50)
    ...
    at PessimisticLockStrategy.lambda$release$1(PessimisticLockStrategy.java:120)
    at PessimisticLockStrategy.release(PessimisticLockStrategy.java:119)
```

→ **TX commit UPDATE thực sự fail vì version mismatch**. Một trong 2 phải đúng:
- (a) DB version đã tăng giữa [L1] và commit (ai đó update song song)
- (b) Hibernate gửi UPDATE với param version SAI (không phải v=X+1 vừa đọc)

Section 5.2-5.4 đưa 3 hypothesis cho cái gì làm assumption ở Section 4 bị break.

### 5.2 Hypothesis A — Outer transaction tồn tại + L1 cache share

**Tiền đề**: Nếu CÓ outer `@Transactional` đâu đó (controller, orchestrator), `transactionTemplate` (default propagation REQUIRED) sẽ JOIN outer tx → cùng EntityManager → cùng L1 cache.

**Kiểm tra**:
```bash
grep -r "@Transactional" hcr-saga/ hcr-product/ms-order/ hcr-inventory/
```

Trong kiểm tra của tôi: `hcr-saga/` → **0 match**, controller → **0 match**.

→ Hypothesis A nhiều khả năng **KHÔNG đúng**, nhưng cần grep lại trên VM thật vì có thể lib hcr-autoconfigure tự thêm `@Transactional` qua AOP advice ở đâu đó không thấy bằng grep.

### 5.3 Hypothesis B — Concurrent update qua code path khác

Lý thuyết Section 4 giả định: giữa [L1] (load v=X+1) và commit, không ai update row.

Suspects (cần đọc code để loại trừ):

1. **`ConcertTicketCatalog`** (`hcr-product/ms-order/.../service/ConcertTicketCatalog.java`):
   - Catalog cache có lưu reference entity managed không?
   - Nếu có, catalog truy cập → entity được attach vào persistence context của thread khác → dirty → flush ngoài ý muốn?

2. **`TicketOrder` entity**:
   - Có field `@ManyToOne ConcertTicket` không? Nếu có, save(order) có thể cascade update concert_tickets.

3. **Hibernate auto-flush trên query khác**:
   - Trong cùng tx, nếu có query đọc concert_tickets (e.g., `getAvailable()` cuối method release line 139), Hibernate auto-flush dirty entities trước query → có thể UPDATE bị "đẩy sớm" lên trước commit, gặp version mismatch.

4. **RedisSeeder** chạy lại:
   - Đã add `@Profile("p3")` nên ở P1 không chạy. Loại.

5. **Reconciliation chạy song song**:
   - Reconciliation cũng có thể UPDATE concert_tickets khi heal stale orders → nếu trùng thời điểm với compensation → race.

**Hành động verify**: bật log Hibernate
```yaml
logging.level.org.hibernate.SQL: DEBUG
logging.level.org.hibernate.orm.jdbc.bind: TRACE
```
→ Sẽ thấy CHÍNH XÁC SQL UPDATE + param version. So sánh với SQL SELECT trước đó.

### 5.4 Hypothesis C — `merge()` trên managed entity gây refresh

Code release line 130: `entityManager.merge(entity)`. Khi entity đã managed (đã load qua find()), `merge()` về lý thuyết là no-op. Nhưng:
- Một số version Hibernate có behavior: merge() trên managed entity với version field có thể trigger version increment lúc flush.
- Nếu merge() copy state từ một entity instance khác có version cũ (case này không có vì cùng instance), version sẽ bị reset.

**Hành động verify**: thử xóa dòng `entityManager.merge(entity)` ở line 130 và 85, build lại, test lại.

### 5.5 Hypothesis D — Spring Data Auditing / Listener

Nếu ConcertTicket entity có `@EntityListeners` hoặc `@PrePersist`/`@PreUpdate` callback, có thể callback chạy UPDATE thêm → tăng version ngoài kiểm soát.

**Hành động verify**: đọc `hcr-product/ms-order/.../domain/ConcertTicket.java` và `AbstractInventoryEntity` xem có listener nào không.

## 6. Fix khả thi — Bypass Hibernate version check ở release()

Dù root cause là Hypothesis nào ở Section 5, fix sau đảm bảo **0% StaleObjectStateException**:

```java
@Override
public void release(String resourceId, String requestId, int quantity) {
    transactionTemplate.execute(status -> {
        // Native UPDATE — bypass @Version, không phụ thuộc L1 cache hay listener
        int rows = entityManager.createNativeQuery(
            "UPDATE concert_tickets " +
            "SET available_quantity = available_quantity + :qty, " +
            "    version = version + 1, " +
            "    updated_at = NOW() " +
            "WHERE resource_id = :id"
        )
        .setParameter("qty", quantity)
        .setParameter("id", resourceId)
        .executeUpdate();

        if (rows == 0) {
            throw new IllegalArgumentException("Resource không tồn tại: " + resourceId);
        }

        // Clear cache để query sau đó không stale
        entityManager.clear();

        // Đọc lại available (fresh) cho event publish
        Long fresh = (Long) entityManager.createNativeQuery(
            "SELECT available_quantity FROM concert_tickets WHERE resource_id = :id"
        ).setParameter("id", resourceId).getSingleResult();

        eventPublisher.publishEvent(
            new ResourceReleasedEvent(resourceId, null, requestId, quantity, fresh, requestId));
        return null;
    });

    metrics.recordReleaseSuccess(resourceId, STRATEGY_NAME);
    metrics.updateAvailableGauge(resourceId, getAvailable(resourceId));
}
```

Đặc điểm fix:
- **Native SQL UPDATE bypass @Version** — không có WHERE version=X, không có cache dependency.
- Version vẫn tăng (+1) để các consumer khác (catalog, optimistic readers) thấy được change.
- `entityManager.clear()` đảm bảo `getAvailable()` sau đó query fresh từ DB.

**Tradeoff**: Native SQL không hưởng Hibernate's optimistic concurrency. Nhưng release() ở compensation path **không cần** check version vì:
- Pessimistic lock đã đảm bảo no concurrent reserve.
- Compensation là deterministic "+1" thay vì conditional UPDATE.
- Không có data loss risk.

### Verify sau fix

Chạy lại oversell-check, expect:
```
sold == COUNT(CONFIRMED)
PENDING count ≠ 0 (vẫn còn nguồn leak 2 — UNKNOWN payment, fix riêng)
```

## 9. Bài học cho thesis

- **Zero oversell ≠ Zero leak**. Phải tách bạch 2 invariant này trong report. Leak là eventual consistency artifact có chủ ý — tradeoff "an toàn cho consistency, hi sinh availability ngắn hạn".
- Tỉ lệ leak measurable: `(sold - CONFIRMED) / total_attempts` = `8/185` ≈ **4.3%** trong run này. Cần nhiều run hơn để có confidence interval.
- **Reconciliation đúng design**: refuse heal khi `UNKNOWN` là chọn safety over availability. Document rõ tradeoff này như feature, không phải bug.
- **Manual heal nguy hiểm**: lệnh "release N vé cho 14 PENDING" trong session này giả định 100% PENDING đã reserve — không đúng → release thừa 6 vé. Production phải có metadata "đã reserve hay chưa" trước khi heal tay.
- **Lý thuyết ≠ thực tế**: Section 4 chứng minh leak không nên xảy ra, Section 5 cho thấy nó vẫn xảy ra. Phần thesis-worthy là **phân tích gap giữa expectation và observation**, không phải chỉ implement xong.
